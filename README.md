# ST. MICHAEL OLD STUDENTS
## Project Report: Alumni Memory & Student Profile Website

### Video Demo
[Watch the Project Demo on YouTube](https://youtu.be/R0MCE5uRuOs?si=ah_KRGIn6PlP8MwU)

---

### 1. Project Overview
St. Michael Old Students is a web-based alumni memory and student profile project. The website is designed to collect and present information about former students of St. Michael School in one organized online location. Visitors can browse old students, search by name, filter by graduation year, and open an individual profile containing basic student information, school memories, and a personal message.

---

### 2. Why This Project Was Created
The main reason for creating this project is to preserve school memories and maintain a connection among former students. After students leave school, photographs, names, friendships, experiences, and memories can become difficult to organize or find. This website provides a simple digital archive where those memories can be kept and shared.

* To preserve memories of St. Michael School and its former students.
* To provide an organized online directory of old students.
* To make student information easy to search and view.
* To give each student a dedicated profile page.
* To provide a foundation for adding more students in the future.
* To practice real-world web development skills through a complete project.

---

### 3. Project Objectives
* Build a simple, responsive and user-friendly alumni website.
* Display student names, photographs and graduation years.
* Allow users to search for students by name.
* Allow users to filter students by graduation year.
* Provide individual student profile pages.
* Provide an administrator interface for adding, editing and deleting student records.
* Move student records from browser-only storage toward an online database so updates can be shared through the public website.

---

### 4. Main Features

| :--- | :--- | :--- |

### 8. How the Website Works

When a visitor opens the home page, JavaScript loads student information and creates student cards dynamically. Clicking a card opens `profile.html` with a student ID in the URL. The profile page reads that ID and displays the matching student's information. The search box filters students by name, while the year selector filters them by graduation year.

The project initially used browser LocalStorage for administrator-added students. Because LocalStorage belongs to a specific browser/device, those records were not automatically visible to visitors on other devices. The project is therefore being upgraded to use Supabase as a shared online database.

---

### 9. Database Plan

The planned Supabase table is named `students`. The main fields are:

| Field | Type | Purpose |
| --- | --- | --- |
| **id** | uuid | Unique student identifier. |
| **name** | text | Student's name. |
| **graduation** | text | Graduation year. |
| **school** | text | School name. |
| **photo** | text | Photo path or URL. |
| **about** | text | Short student biography. |
| **memories** | text | School memories. |
| **message** | text | Student's personal message. |
| **created_at** | timestamp | Record creation time. |

---

### 10. Administration Workflow

1. Administrator opens the Admin page.
2. Administrator signs in.
3. Administrator enters the student's information.
4. The record is saved to the online Supabase database.
5. The public website reads the database and displays the student.
6. Administrator can later edit or delete the record.

---

### 11. Deployment

The website is published using GitHub Pages. This provides public web hosting for the HTML, CSS, JavaScript and other static website files. Supabase is used separately as the online backend/database so that student records can be shared rather than being limited to one browser's LocalStorage.

---

### 12. Security and Privacy Considerations

* The current client-side username/password login is suitable only for development/testing and should not be treated as secure production authentication.
* For a public production version, administrator authentication should use Supabase Auth or another secure authentication system.
* Database Row Level Security (RLS) should be configured so public visitors can read appropriate student records while only authorized administrators can add, edit or delete records.
* Secret or service-role keys must never be placed in public JavaScript code.
* Student photographs and personal information should be published only with appropriate permission.
* Sensitive information such as home addresses, phone numbers, identification numbers and private contact details should not be publicly displayed.
